# ESP32 网关处理能力估算（CPU / RAM / SPI / GPIO / 时隙定时）

> 目的：评估 ESP32 作为基地台网关的算力余量——T1 单信道（当前实现）与
> T3 3 信道（**50 台目标**，2026-09-13 修订）两个场景。所有数值为**工程估算**，标注单位，
> 最终以实测校准为准（本文末尾附实测清单）。

## 1. 结论摘要

| 场景 | 结论 |
| --- | --- |
| **T1 单信道（17 设备，当前固件）** | ✅ **绰绰有余**：单核峰值占用 <15%，RAM 富余 |
| **T3 3 信道（3×SX1268，50 台）** | ✅ **CPU / RAM / GPIO / SPI 全部宽裕**：3 个 MAC 任务共 48KB 栈、1 条 SPI 总线 ≈11% 占用、GPIO 只需 3×2+1=7 根。原「12 信道」方案的瓶颈（任务合并、第二条总线、错峰）**全部消失**；唯一仍需做的是**非阻塞 TX** |
| ~~SX1302 集中器路线~~（**已作废**） | 那是为 8~16 信道并发解调准备的；50 台只需 3 信道，用不上，**不采用** |

## 2. ESP32 资源盘点

| 资源 | ESP32 经典款（ESP32-D0WD） | ESP32-S3（推荐 T3） |
| --- | --- | --- |
| CPU | 双核 Xtensa LX6 @ 240MHz | 双核 LX7 @ 240MHz |
| SRAM | 520KB 总，应用可用 ~200-280KB（WiFi 协议栈占用后） | 512KB，可用 ~300-400KB |
| 用户 SPI 总线 | **2 条**（VSPI=SPI2 / HSPI=SPI3；SPI0/1 保留给 flash/PSRAM） | 3 条（SPI2/3 可配） |
| 可用 GPIO | ~26-30 | ~40+ |
| Flash | 4MB | 4-16MB |

## 3. T1 单信道负载核算（当前实现，1×SX1262）

### 3.1 射频任务（TDMA MAC，core 1 优先级 5）——每 200ms 超帧

| 环节 | 耗时 | 说明 |
| --- | --- | --- |
| 信标 TX + 下行 TX | 2 × 9.3ms **忙等** | RadioLib `transmit()` 阻塞轮询 IRQ；空口时间物理占用 |
| 上行 18 时隙 RX 轮询 | ~7.2ms 分散 | 每时隙窗 ~10 次 `readData()`（每次 SPI ~20-50µs），`vTaskDelay(1)` 让出 CPU |
| 注册时隙 + 重排 | ~1ms | 忽略 |
| **射频任务合计** | **~13% 单核**（其中 TX 忙等 9.3%） | 峰值，非持续 |

### 3.2 主循环（core 1 低优先级：WiFi/WS/JSON/显示）

| 负载 | 估算 |
| --- | --- |
| WebSocket 维护 `ws.loop()` | 无数据时 ~10-50µs/循环 |
| 事件 JSON 序列化（ArduinoJson 7） | 每事件 ~100-300µs |
| 事件速率（17 设备）：心跳 2/s + 命中/阵亡 ~5-10/s + 位置 ~2/s | 峰值 ~30 帧/s → **<1% CPU** |
| OLED 500ms 节流 + 组播 | 可忽略 |
| **主循环合计** | **~3-5% 单核** |

### 3.3 T1 结论

- 单核峰值占用 **<15%**，另一核空闲（WiFi 在 core 0）；
- RAM：WiFi ~40KB + 任务栈 32KB + 队列 ~1KB + 堆 → 总 ~120-180KB，余量充足；
- **ESP32 做单信道网关非常轻松，还有 3-4 倍余量**（可同时承担本地组播/大屏/语音）。

## 4. T3 3 信道负载核算（目标 50 台，3×SX1268）

### 4.1 CPU：够用（有条件）

- 3 信道 × 每信道 2 帧 TX（信标+下行）= **6 次 TX/200ms**，若沿用阻塞 transmit
  忙等 = 6 × 9.3ms = 56ms/200ms → 单核 **28%**（原 12 信道方案是 24 次 / 112% ✗）。
  仍有 28% 是白等，**非阻塞化照做**（收益从「救命」变成「省 28%」）。
- **对策（必须）**：非阻塞发射（RadioLib `startTransmit()` + DIO1 中断回调，
  或忙等循环内 `vTaskDelay(1)`），把 TX 忙等降到 ~0 → TX 期间 CPU 让出。
- 信道相位**错峰**（可选）：3 信道的超帧起点错开 200/3 ≈ 60ms，纯粹为削峰；
  **非必需** —— 3 信道间隔 ≥18MHz，同时发射也不会互相阻塞。
- RX 轮询：**3 信道 × 3.6% ≈ 11% 单核**（原 12 信道 43%）。
- 主循环 ~2%（JSON 事件 50 台，上限 ~51 帧/s × 0.3ms ≈ 2%）。
- **每核峰值 ~15-20%** ✅（即使 TX 未非阻塞化也不超载）。

### 4.2 RAM：最大瓶颈

| 项 | 当前 | 问题 | 对策 |
| --- | --- | --- | --- |
| MAC 任务栈 | 4096 字 = **16KB/任务**（可配 `TDMA_TASK_STACK_WORDS`） | **3 任务 = 48KB**，ESP32-S3 上完全宽裕（原 12 任务 192KB ✗ 已成历史） | 无需任务合并；实测可降到 2048-3072 字 |
| WiFi 协议栈 | ~40KB | — | — |
| 队列/缓冲 | ~8KB | — | — |
| 堆（JSON/WS 缓冲） | 预留 ~80-100KB | — | — |
| **合计** | — | — | **~180-220KB**：ESP32 经典款紧张，**ESP32-S3 从容** |

> RadioLib 调用链（SPI+ISR）+ Serial.printf 栈较深；单射频 4096 字足够，多射频
> 合并任务后 4096 字/任务仍可。任务栈高水位用 `uxTaskGetStackHighWaterMark` 实测。

### 4.3 SPI 总线：可行但需 2 条 + 互斥

- 3 射频共用 **1 条总线**（SCLK/MOSI/MISO 共享，NSS 各自选通）：
  - 每信道每超帧 ~180 次 SPI 事务 × 40µs = 7.2ms → 3 信道 ≈ **11% 占用** ✅（**不需要第二条总线**）
- **必须**：同一总线多射频的 NSS 切换需**互斥锁**（SPI 事务原子化）；
  建议 SPI 时钟 ≥8MHz（SX1262 上限 ~16MHz，RadioLib 默认走 8MHz 档，可提）。
- 单条总线大致可撑到 ~8 射频（≈30% 占用）才需要第二条。

### 4.4 GPIO：3 射频只需 7 根，非常宽裕

- 3 射频 × (NSS + BUSY) = 6 引脚 + 共享 SPI 四线（SCLK/MOSI/MISO）= 3 + **RST 共用 1**
  + 状态灯 1 + OLED 2 → **约 13 根**；
- **ESP32-S3 可用 ~30+ → 绰绰有余**（原 12 射频方案要 ~36 根，经典款 ESP32 不够）。
- **RST 可以多模块共用一根**：正常运行时 NRESET 只需保持高电平，只有上电初始化时才拉低
  （逐个 `begin()` 即可，代价是"复位一个=复位全部"，仅影响初始化时序，不影响运行）。
- **DIO1 不必每射频一根**（轮询 IRQ 寄存器已实现，见 `docs/lora-gateway-test.md` §4.1）；
  若想给某个射频做精确 TX-done 中断，单独接一根即可（槽 0 已接 G04）。
- 结论：3 射频下引脚完全不是问题，**剩余引脚还能再扩到 8 射频**（8×2+1=17 根）。

### 4.5 吞吐与延迟边界

| 项 | 值 | 判定 |
| --- | --- | --- |
| 系统上行帧上限 | 3 信道 × 17 时隙 = **51 帧/s** | TDMA 物理上限（50 台目标） |
| 网关处理 51 帧/s（SPI+CRC+JSON+WS） | ~51 × 0.4ms ≈ **2% 单核** | ✅ |
| WiFi 上行带宽（51 帧 × ~300B JSON） | ~15KB/s ≈ 0.12Mbps | ✅ 远低于 WiFi 实际吞吐 |
| WebSocket 发送 | 库内部异步缓冲 + `ws.loop()` 驱动 | ✅ 不阻塞射频任务 |
| 时延 | 由超帧决定（N=17 → 200ms 单跳），与网关算力无关 | ✅ |

## 5. 三条实现路线对比（T3 网关硬件）

| 路线 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **A：3×SX1268 多射频板（ESP32-S3）** | 与现有 RadioLib/TdmaMac 完全兼容；3 个信道正好覆盖 50 台；模组便宜（¥25-35×3）；**RAM/GPIO/SPI 全部宽裕**（每模块只需 NSS+BUSY，RST 可共用） | 仍需非阻塞 TX；多模块同板需频率间隔（本方案 ≥18MHz，几乎无风险） | **✅ 定案** |
| ~~B：2×SX1302 集中器~~ | — | **已作废**：50 台只需 3 信道，用不上 8~16 路并发解调；且通常要配 Linux 主控 | ✗ |
| C：多 ESP32 网关分摊信道 | 单机负载更低、冗余 | "全信道覆盖"要求每网关配齐 3 射频 → 成本 ×网关数；多网关共听/漫游机制（T4）本就支持，按需启用 | △ 场地分区大时辅助 |

> 参考：ESP32 + SX1302 有成功产品（如 [The Things Indoor Gateway Pro](https://www.tecnohub.org/2024/09/the-things-indoor-gateway-pro-feature.html)），
> 但均为 Linux/专用固件 + 大 RAM 场景；本项目 TDMA 静态信道规划下多 SX1262 更匹配。

## 6. 瓶颈与对策清单（T3 落地必做）

1. **TX 非阻塞化**（轮询 IRQ 寄存器，已落地）：消除 6×9.3ms/200ms 忙等 → 单核省 ~28%。
2. ~~任务合并~~（**不再需要**）：3 个 MAC 任务共 48KB 栈，ESP32-S3 上宽裕。
3. **1 条 SPI 总线 + NSS 互斥锁**（3 射频 ≈11% 占用，无需第二条总线）。
4. **信道相位错峰**（可选，纯削峰）：超帧起点错开 ~60ms。
5. **主控用 ESP32-S3**（已换）：RAM 512KB、GPIO 40+、SPI 更快。
6. **时隙抖动**：WiFi 协议栈在 core 0 且优先级高（18-23），会抢占 core 0 上的
   MAC 任务 → MAC 任务固定 core 1 + 忙等末段短（≤1ms）+ 保护间隔 0.7ms 已吸收；
   若实测抖动超限，错峰 + 增大保护间隔（代价：时隙数下降）。
