# ESP32 网关处理能力估算（CPU / RAM / SPI / GPIO / 时隙定时）

> 目的：评估 ESP32 作为基地台网关的算力余量——T1 单信道（当前实现）与
> T3 12 信道（200 设备目标）两个场景。所有数值为**工程估算**，标注单位，
> 最终以实测校准为准（本文末尾附实测清单）。

## 1. 结论摘要

| 场景 | 结论 |
| --- | --- |
| **T1 单信道（17 设备，当前固件）** | ✅ **绰绰有余**：单核峰值占用 <15%，RAM 富余 |
| **T3 12 信道（12×SX1262，200 设备）** | ⚠️ **CPU 算力够，瓶颈在 RAM（任务栈）与 GPIO 引脚数**；需任务栈瘦身 + 2 条 SPI 总线 + 非阻塞 TX + 信道相位错峰；**建议主控换 ESP32-S3** |
| SX1302 集中器路线（备选） | 省 CPU 但开发量大、成本高；本项目静态信道规划用不上其灵活性，**不推荐为主路线** |

## 2. ESP32 资源盘点

| 资源 | ESP32 经典款（ESP32-D0WD） | ESP32-S3（推荐 T3） |
| --- | --- | --- |
| CPU | 双核 Xtensa LX6 @ 240MHz | 双核 LX7 @ 240MHz |
| SRAM | 520KB 总，应用可用 ~200-280KB（WiFi 协议栈占用后） | 512KB，可用 ~300-400KB |
| 用户 SPI 总线 | **2 条**（VSPI=SPI2 / HSPI=SPI3；SPI0/1 保留给 flash/PSRAM） | 3 条（SPI2/3 可配） |
| 可用 GPIO | ~26-30 | ~40+ |
| Flash | 4MB | 4-16MB |

## 3. T1 单信道负载核算（当前实现，1×SX1262）

### 3.1 射频任务（TDMA MAC，core 1 优先级 5）——每 200ms 超帧

| 环节 | 耗时 | 说明 |
| --- | --- | --- |
| 信标 TX + 下行 TX | 2 × 9.3ms **忙等** | RadioLib `transmit()` 阻塞轮询 IRQ；空口时间物理占用 |
| 上行 18 时隙 RX 轮询 | ~7.2ms 分散 | 每时隙窗 ~10 次 `readData()`（每次 SPI ~20-50µs），`vTaskDelay(1)` 让出 CPU |
| 注册时隙 + 重排 | ~1ms | 忽略 |
| **射频任务合计** | **~13% 单核**（其中 TX 忙等 9.3%） | 峰值，非持续 |

### 3.2 主循环（core 1 低优先级：WiFi/WS/JSON/显示）

| 负载 | 估算 |
| --- | --- |
| WebSocket 维护 `ws.loop()` | 无数据时 ~10-50µs/循环 |
| 事件 JSON 序列化（ArduinoJson 7） | 每事件 ~100-300µs |
| 事件速率（17 设备）：心跳 2/s + 命中/阵亡 ~5-10/s + 位置 ~2/s | 峰值 ~30 帧/s → **<1% CPU** |
| OLED 500ms 节流 + 组播 | 可忽略 |
| **主循环合计** | **~3-5% 单核** |

### 3.3 T1 结论

- 单核峰值占用 **<15%**，另一核空闲（WiFi 在 core 0）；
- RAM：WiFi ~40KB + 任务栈 32KB + 队列 ~1KB + 堆 → 总 ~120-180KB，余量充足；
- **ESP32 做单信道网关非常轻松，还有 3-4 倍余量**（可同时承担本地组播/大屏/语音）。

## 4. T3 12 信道负载核算（目标 200 设备，12×SX1262）

### 4.1 CPU：够用（有条件）

- 12 信道 × 每信道 2 帧 TX（信标+下行）= 24 次 TX/200ms，**若沿用阻塞 transmit
  忙等 = 24 × 9.3ms = 223ms/200ms → 单核 112% ✗ 超载**。
- **对策（必须）**：非阻塞发射（RadioLib `startTransmit()` + DIO1 中断回调，
  或忙等循环内 `vTaskDelay(1)`），把 TX 忙等降到 ~0 → TX 期间 CPU 让出。
- 信道相位**错峰**：12 信道的超帧起点错开 200/12 ≈ 16.7ms，避免 12 个任务同时
  忙等/抢占同一核。
- RX 轮询：12 信道 × 3.6% ≈ 43% 单核 → 分布在 2 核，各 ~22%。
- 主循环 ~5-10%（JSON 事件 200 设备 ~200 帧/s × 0.3ms ≈ 8%）。
- **优化后每核峰值 ~35-45%** ✅（若 TX 未优化则必然超载 ✗）。

### 4.2 RAM：最大瓶颈

| 项 | 当前 | 问题 | 对策 |
| --- | --- | --- | --- |
| MAC 任务栈 | 4096 字 = **16KB/任务**（可配 `TDMA_TASK_STACK_WORDS`） | 12 任务 = **192KB ✗ 超 RAM**；创建失败已会跳过该射频 | 实测降到 2048-3072 字；**改 2-4 个任务，每任务管 3-6 射频** → 4×8KB=32KB |
| WiFi 协议栈 | ~40KB | — | — |
| 队列/缓冲 | ~8KB | — | — |
| 堆（JSON/WS 缓冲） | 预留 ~80-100KB | — | — |
| **合计** | — | — | **~180-220KB**：ESP32 经典款紧张，**ESP32-S3 从容** |

> RadioLib 调用链（SPI+ISR）+ Serial.printf 栈较深；单射频 4096 字足够，多射频
> 合并任务后 4096 字/任务仍可。任务栈高水位用 `uxTaskGetStackHighWaterMark` 实测。

### 4.3 SPI 总线：可行但需 2 条 + 互斥

- 12 射频分到 2 条总线（VSPI/HSPI 各 6）：
  - 每信道每超帧 ~180 次 SPI 事务 × 40µs = 7.2ms → 每总线 6 信道 ≈ **22% 占用** ✅
- **必须**：同一总线多射频的 NSS 切换需**互斥锁**（SPI 事务原子化）；
  建议 SPI 时钟 ≥8MHz（SX1262 上限 ~16MHz，RadioLib 默认走 8MHz 档，可提）。
- 若单条总线 12 射频 → 44% 占用，偏紧（且 12 NSS 时隙错峰仍会排队）。

### 4.4 GPIO：ESP32 经典款不够，S3 才行

- 12 射频 × (NSS + BUSY) = 24 引脚 + 2 总线 × 3 共享（SCLK/MOSI/MISO）= 6 + RST
  共用 1 + 状态灯/按键/OLED ~5 → **~36 引脚**；
- ESP32 经典款可用 ~26-30 → **不够**；**ESP32-S3（~40+）合适**。
- 备选：DIO1 可不接（轮询模式，本项目已如此）→ 省 12 引脚，但牺牲非阻塞 TX
  中断路径（与 4.1 对策冲突，需权衡：DIO1 接上做 TX-done 中断最理想）。

### 4.5 吞吐与延迟边界

| 项 | 值 | 判定 |
| --- | --- | --- |
| 系统上行帧上限 | 12 信道 × 17 时隙 = **204 帧/s** | TDMA 物理上限 |
| 网关处理 204 帧/s（SPI+CRC+JSON+WS） | ~204 × 0.4ms ≈ **8% 单核** | ✅ |
| WiFi 上行带宽（204 帧 × ~300B JSON） | ~61KB/s ≈ 0.5Mbps | ✅ 远低于 WiFi 实际吞吐 |
| WebSocket 发送 | 库内部异步缓冲 + `ws.loop()` 驱动 | ✅ 不阻塞射频任务 |
| 时延 | 由超帧决定（N=17 → 200ms 单跳），与网关算力无关 | ✅ |

## 5. 三条实现路线对比（T3 网关硬件）

| 路线 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **A：12×SX1262 多射频板（ESP32-S3）** | 与现有 RadioLib/TdmaMac 完全兼容；12 个固定信道正是我们的静态规划；模组便宜（¥25-35×12） | RAM 紧张（需任务合并）、GPIO 吃紧、SPI 分总线+互斥、时隙错峰开发 | **✅ 推荐主路线** |
| B：2×SX1302 集中器 | 硬件 8 信道并发解调，CPU 负载极低；包级处理 | 初始化/校准复杂（通常配 Linux）；成本 ¥600-1200；ESP32 裸机驱动开发量大；TX 需额外射频；8 信道/片粒度与 12 信道错配 | ⚠️ 备选（量级更大/主控换 Linux 板时） |
| C：多 ESP32 网关分摊信道 | 单机负载更低、冗余 | "全信道覆盖"要求每网关配齐 12 射频 → 成本 ×网关数；或接受信道=区域静态映射（覆盖盲区） | △ 场地分区大时辅助 |

> 参考：ESP32 + SX1302 有成功产品（如 [The Things Indoor Gateway Pro](https://www.tecnohub.org/2024/09/the-things-indoor-gateway-pro-feature.html)），
> 但均为 Linux/专用固件 + 大 RAM 场景；本项目 TDMA 静态信道规划下多 SX1262 更匹配。

## 6. 瓶颈与对策清单（T3 落地必做）

1. **TX 非阻塞化**（DIO1 中断）：消除 24×9.3ms/200ms 忙等 → 单核省 ~50%。
2. **任务合并**：2-4 个 MAC 任务，每任务管 3-6 射频（RAM 从 384KB 降到 ~32-48KB）。
3. **2 条 SPI 总线 + 互斥锁**：每总线 6 射频（占用 ~22%/条）。
4. **信道相位错峰**：超帧起点错开 16.7ms，避免同核多任务同时忙等。
5. **主控换 ESP32-S3**：RAM 512KB、GPIO 40+、SPI 更快——一步到位。
6. **时隙抖动**：WiFi 协议栈在 core 0 且优先级高（18-23），会抢占 core 0 上的
   MAC 任务 → MAC 任务固定 core 1 + 忙等末段短（≤1ms）+ 保护间隔 0.7ms 已吸收；
   若实测抖动超限，错峰 + 增大保护间隔（代价：时隙数下降）。
