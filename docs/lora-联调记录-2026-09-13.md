# LoRa 联调记录 · 2026-09-13（单信道闭环打通）

> 目标：**先把单信道闭环跑通**（枪端扫描选频 → 锁相 → JOIN → 收到 ASSIGN → 在自身时隙发帧）。
> 结论：**已打通，并稳定运行 5 分钟**（网关 `devs=1` 全程不掉、无 `expire`、`devHb` 序号连续）。
>
> 起点是"网关开机 `FATAL: no radio up`、枪端永远 `reg=no`"，一路查出 9 个独立缺陷。
> 本文按"现象 → 根因 → 修法 → 证据"记录，供后续接续。

## 2. 九个缺陷（现象 → 根因 → 修法）

### 2.1 网关开机误报 `FATAL: no radio up`（自检探针把矛头指向"焊接/供电"）

- **现象**：刷 `gateway` 后每 2s 重复 `FATAL: no radio up … 本机已检测到 0 个槽位`。
- **根因**：`probeSlot()` 跑在 `RadioLink::begin()` **之前**，而全工程唯一驱动 RST 的地方是
  RadioLib 的 `SX126x::reset()`（在 `begin()` 里）。G46 是 ESP32-S3 的 strapping 脚，
  未配置时由内部弱上拉/下拉决定电平，NRESET 被 SX1268 内部 ~50k 上拉与 S3 弱下拉分压
  ≈1.6V → 落在阈值不确定区 → 芯片可能一直停在复位态、SPI 不应答。
  对照：`spi-read` 能读到版本串，正因为它显式驱动 RST 并做复位脉冲。
  另有两处错：探针读的是 **0x0333**（RadioLib 未定义），版本串在 **0x0320**；
  且把 `rx[3]` 当数据首字节（实际是**状态字节**，数据从 `rx[4]` 起）。
- **修法**（`gateway/src/main.cpp`）：探针自己 `pinMode(rst,OUTPUT)` + 拉高 + 2ms 复位脉冲，
  先读一次 RST 原始电平（`before=` 诊断），再读 0x0320 十六字节并按 `ver="SX126…"` 判在位。

### 2.2 网关 WiFi 段阻塞开机（即使射频起来了也看不到心跳）

- **现象**：`setup()` 末尾 `while (WiFi.status() != WL_CONNECTED) { delay(500); }`，
  而 SSID/服务器是占位值 → 永远连不上、`loop()` 一行都不跑。
- **修法**：新增总开关 `GW_WIFI_ENABLE 0` + `GW_MIRROR_UPLINK_SERIAL 1`
  （本该发服务器的 JSON 镜像成串口 `[up-json]` 行 → 不接服务器也能看见上行内容）。
  副产品：WiFi+mbedTLS 不再链接，RAM 63.5KB→36KB、Flash 950KB→327KB。

### 2.3 OLED / 状态灯是"经典 ESP32 残留引脚"

- **现象**：网关 OLED 不亮、状态灯不亮。
- **根因**：`PIN_OLED_SDA/SCL = 21/22` 是经典 ESP32 的默认 I2C 脚，而 **ESP32-S3 没有 GPIO22**；
  `PIN_STATUS_LED = 2` 是经典板载 LED 脚，S3 上 G2 是空脚（枪端把 G2 当按键用）。
- **修法**：OLED 改 **G17/G18**（与枪端一致，代码零改动——两端都是 `U8G2_SSD1306_128X64_NONAME_F_SW_I2C`）；
  状态灯改 **G48**（模组板载 LED，**普通单色灯、不是 WS2812**、灌电流接法 → **低电平点亮**）。
  枪端 `LedStrip` 随之从 FastLED/WS2812 改写为单色版（"颜色"→**闪烁节奏**），
  接口不变、调用点不动，`gun/platformio.ini` 的 `fastled` 依赖移除。

### 2.4 扫描选频靠"随机平局" → 锁到假信标

- **现象**：枪端 `ch17 selected`（504MHz），而网关在 472MHz → 永远注册不上。
- **根因**：`scan` 只按 `score = N*100 + random(0..99)` 打分，两个候选 N 相同就**纯随机**。
- **修法**：**确证式扫描**——单频点停留 250ms，收满窗内所有帧，统计"信标个数 ≥2"且
  "超帧计数器逐一递增"才判定为本网网关；未确证的只作兜底。负载均衡（按 N 择优）保留。

### 2.5 幻影信道：+16MHz / +32MHz 杂散

- **现象**：扫描同时"确证"了 ch1(472)、ch9(488)、ch17(504) 三个频点，且都 `counter=ok`。
- **根因**：当时只有**一块**网关板在 472MHz 发射。`472+16=488`、`472+32=504`
  （16 = 晶振 32MHz/2）——两板相距十几厘米时电平足够强，**杂散被解成完整合法包**。
  栅格是 `470+2k`、470 以下无信道 → 只有正向偏移落在栅格点上，恰好 ch9/ch17。
- **修法**：2.4 的确证式扫描 + **注册自愈**（见 2.6）。这是**间歇性**故障：后一次扫描就只
  确证了 ch1 —— 所以两道保险必须长期保留。附带结论：网关开机扫描测到的
  `freq 18/19 (506/508MHz) avg=-36 max=-36` 也是近场泄漏把接收机压住的表现。

### 2.6 ASSIGN 只发一次 → 丢一次就永久注册不上

- **现象**：网关 `devs=1`、`join` 只打印一次，但设备每 600ms 重发 JOIN，永不进入时隙。
- **根因**：`onGwUplink` 对"已登记设备"直接 `return`；而 ASSIGN 只在首次 JOIN 时入队一次，
  网关每超帧又只发 1 帧下行 → 那帧丢了就再无重发。
- **修法**：对已登记设备的**重复 JOIN 补发 ASSIGN**（`sendAssign()`，**不重排**，slot/N/ver 不变，
  幂等）；`slot=0xFF`（信道满）改走 `advanceCandidate()` 换候选信道（原先"重新全表扫描"
  可能又选回同一满信道）。

### 2.7 mapVer 位宽不一致（潜伏 bug，一并修掉）

- 信标里 `mapVer` 只有 **3 bit**（`payload[4] = (mapVer<<5) | N`），而 ASSIGN 发的是整个字节，
  设备端却直接比较 `_beaconMapVer == _mapVer` → **`_mapVer ≥ 8` 时永远对不上**，
  症状与 2.6 一模一样。修法：ASSIGN 侧统一 `(_mapVer & 0x07)`。

### 2.8 【关键】下行全丢：信标窗与下行窗之间没有重新武装 RX

- **现象**：网关日志明确显示"每次收到 JOIN 就补发 ASSIGN"（`re-assign` 刷屏、`devs=1`），
  而枪端 30 秒内一次都没进 `assigned` —— **上行通、下行全丢**。
- **根因**：原实现把信标窗与下行窗写成**两次独立轮询**，注释里"射频仍在 RX（连续模式，
  未重武装）必然被捕获"是**错误假设**——RX_DONE 之后芯片并不保证留在 RX。
  网关下行帧在信标结束后约 **1ms** 就发，**前导只有 4 符号（SF7/BW500k ≈ 2.1ms）**，
  错过前导整帧即丢；而轮询粒度是 `vTaskDelay(1)` = **1ms**，足以错过。
- **修法**：① 读完信标**立刻重新武装 RX** 再进下行窗；② 两个窗都改**细粒度轮询**
  （`delayMicroseconds(200)`，`readPacketPoll(..., fine=true)`）；
  ③ 抽出 `applyAssign()`，ASSIGN 落在信标窗尾也一并消费（原先会被当普通帧丢进应用队列，MAC 永远看不到）。
- **同一根因的第二个症状（顺带修好）**：粗粒度轮询让设备相位基准偏晚约 1ms，
  JOIN 落在网关注册窗（`T_REG 10ms + 6ms 余量`）边缘被大量漏掉——这解释了修复前
  "60 秒只收到 4 次 JOIN、`re-assign` 每 5~6 秒才一次"。

### 2.9 `txFrame()` 起发失败静默

- 原来 `if (_r->startTransmit(...) != RADIOLIB_ERR_NONE) return;` —— 帧已被 `ringPop` 出队，
  一旦起发失败就**永久丢失**且无任何日志。现改为打印 `txFrame: startTransmit 失败，该帧丢失`。

## 3. 当前能力与已知限制（单信道）

| 项 | 现状 |
| --- | --- |
| 吞吐 | 单信道 17 时隙；超帧 `30+10N ms`（N=1 → 47ms；N=17 → 200ms） |
| 上下行 | 上行：每设备每超帧 1 帧；**下行：每超帧只有 1 帧** ← 瓶颈 |
| 注册 | 每超帧 1 个注册窗（10ms = 1 帧容量）；设备每 3 超帧试一次 + 0~6ms 抖动 |
| 稳定性 | 5 分钟 `devs=1` 不掉、无 `expire` ✓ |

**两个必须在 50 台目标前解决的问题：**

1. **下行容量**：每超帧只有 1 帧 = N=17 时 5 帧/s。当前每个补发的 ASSIGN 都要占这一帧，
   而枪端应用层每 5s 就重发一次 J 帧（等 W 帧）→ 50 台时会有 ~10 次/s 的 ASSIGN 请求，
   **远超下行窗排水能力，会把下行窗占满**（W/S/E 等下行帧被饿死）。
   → 需要"**每设备补发 ASSIGN 节流**"（如每台 ≥2s 一次），或加宽下行窗。
2. **注册重试太密**：设备"每 3 超帧"确定性重试 + 单注册窗（一窗一帧）→ 50 台冷启动会撞死
   （按时隙 ALOHA 估算，G≈5.7 时每窗成功率仅 ~0.02，收敛可能要分钟级）。
   → 需要"**真·时隙 ALOHA**"（随机子槽 + 随机重试间隔）+ **自适应注册窗**（有未注册设备时
   临时开 2~3 个子槽，稳态缩回 1 个，保证 N=17 时超帧仍是 200ms）。

## 6. 同日下午追加：任务 1/2（下行容量保护 + 注册时隙 ALOHA）

闭环打通后立刻做了 §3 里标记为"50 台目标硬门槛"的两项。

### 6.1 任务 1：ASSIGN 补发精确化（下行容量保护）

**关键洞察**：设备侧有两类 JOIN，网关可以**从来源区分**：

| JOIN 来源 | 含义 | 是否该补发 ASSIGN |
| --- | --- | --- |
| **注册窗**（设备没有时隙才会来这里） | 它确实没拿到 ASSIGN | ✅ 补发 |
| **设备自己的时隙** | 已注册，只是还没收到服务器 W 帧（`REJOIN_MS 5000` 重发 J） | ❌ 补发毫无意义 |

原实现两类都补发 → 50 台 × 每 5s ≈ **10 次/s** 的 ASSIGN 请求，远超下行窗排水能力
（每超帧只发 1 帧 = N=17 时 5 帧/s）→ W/S/E 等下行帧会被饿死。

**改法**：`onGwUplink(f, fromRegSlot)`——只有来自注册窗的 JOIN 才补发；注册窗每超帧
最多进 1 帧，所以**补发率天然被限死在 ≤1 帧/超帧 = 下行容量本身**，结构上不可能挤占
其它下行帧。另加每设备 `ASSIGN_RESEND_MIN_MS = 1000` 节流兜底。

### 6.2 任务 2：注册时隙 ALOHA + 自适应注册窗

**原问题**：设备"每 3 个超帧试一次 + 0~6ms 抖动"是**确定性节拍** → 多台同时开机时
挤进同一个 10ms 注册窗撞成一团。按时隙 ALOHA 估算 G≈5.7 时每窗成功率仅 ~0.02
（`S = G·e^-G`），50 台冷启动收敛要分钟级。

**改法**：

1. **设备：真·时隙 ALOHA**——每次尝试后重抽 **1~8 超帧的随机等待**（把同步风暴打散成
   独立到达）；在注册窗内**随机选一个子槽**，子槽内再加 0~0.5ms 抖动
   （帧 9.28ms < 子槽 10ms，抖动必须远小于子槽，否则跨槽碰撞）。
2. **网关：自适应注册窗**——有新设备注册后把注册窗临时开到 **3 个子槽**（持续 5s，
   每次新注册刷新），静默 5s 后缩回 **1 个**，保证稳态超帧仍是 `37+10N ms`。
3. **信标广播子槽数**（`payload[4]` 低 2 位，见 `docs/protocol-tdma.md` 0x00 BEACON），
   两端据此算出**相同**的超帧长度——否则注册突发时网关超帧长 20ms，设备按旧公式会
   提前 27ms 醒、错过信标而失锁。
4. **顺带修掉一个相位漂移**：设备原来在超帧末尾用"本地推算值"计算下一超帧起点
   （且漏了 `T_SF_TAIL`），信标校正出的真实相位被覆盖 → 晶振漂移逐帧累积。
   现在每超帧**采用信标校正后的相位**（`sfStart = _sfStartUs`）并用与网关**完全相同**的
   公式推算。这解释了 5 分钟测试里 `devHb` 序号有明显丢包（5→6→8→12→14…）。

**预期效果**：注册吞吐从"每窗成功率 0.02"提升到时隙 ALOHA 的理论值（G≈1 时 0.37/槽），
配合 3 子槽突发窗，50 台冷启动收敛从"分钟级"降到 **数秒级**。

**离线验证手段（待做）**：手上只有 2 块板，压不出"多台并发注册"。计划加一个
**"模拟 N 台设备并发注册"的测试模式**（单板伪造 N 个不同 devIdx 的 JOIN，按随机子槽
发出），一次上板即可测出注册收敛曲线与时隙命中率。

### 6.3 改版后的兼容性注意

信标 payload 布局变了（计数 4B→3B，新增标志字节）→ **枪端与网关必须同时升级**。
`lora-gwtest` / `gun-selftest` 各自带**独立的 MAC 副本**（`LoRaTest` / `LoRaDev`），
未同步此改动，**与正式固件不再互通**——它们只能"自己跟自己"对测。

### 6.4 回归与修复：改信标格式时漏改了一处解析（同日，**自己造成的**）

**现象**（重烧后）：`scan ch17(504.0MHz): 3 beacon(s), counter=NO(sf=2817)` →
候选被标"未确证" → 锁上后 `join try` 刷屏、`reg=no` 永不变化。

**根因**：§6.2 改信标 payload 布局时，发送端（`runGateway`）与接收端
（`lockFromBeacon`）都改了，**但扫描取证用的 `dwellBeacon()` 漏改**，仍按旧的
**4 字节**计数器读 → 新格式下读到 `≈计数器<<8`，相邻信标差 **256** 而非 1 →
"确证"判定永远失败；`N` 也从 `payload[4]`（现在是子槽数）读成了 1 或 3。

**修法**：

1. `dwellBeacon()` 按新布局解析（计数器 3 字节 / N 在 `payload[3]` / 子槽数在 `payload[4]`）；
2. 计数器判据放宽为**"递增且跨度 ≤16"**——原来要求恰好 +1，**漏掉 1~2 个信标就会把
   真网关误判成"未确证"**（本次同时暴露了这个脆弱点）；
3. **新增信标协议版本号 `TDMA_PROTO_VER`**（随信标 `payload[4]` 高 6 位广播）：设备解析
   信标时**先校验版本**，不匹配就不当作本网信标并打印明确告警。这类"改了一处漏了另一处"
   的故障以后会**直接报出来**，而不是表现为难以定位的"锁得上但注册不上"。
   **改动信标/帧格式时必须递增该值。**

**教训**：一次格式变更必须同时覆盖「**发送端 / 接收解析 / 扫描取证**」三处；
靠人记不如靠版本号校验——这是本次交付里唯一一个自己造成的回归，留档备查。

## 8. 当日晚间续：双设备闭环打通 + 协议 v3 + 若干实测坑

### 8.1 结果（实测）

**单信道、双设备闭环稳定运行**（枪端 A/B 均为枪端板，网关为同一板型的另一块）：

```
枪端: [gun] identity: deviceId="G30MW" devIdx=198 MAC=…   ← 两台 MAC/身份不同
      [tdma] 采用网关分配的 devIdx=1（本机自报 133）
      [tdma] assigned ch1 slot1 N2 ver0
      [gun] t=7s … TDMA=run+locked ch=1 slot=1 …            ← 稳定 3 分钟以上
网关: [tdma] ch1 join devId="G3J28"(自报号 133) -> 分配 idx=1，共 2 台
      [gw] rx/s: slot=1 reg=0 | n=2 regSlots=1 devs=2
```

### 8.2 三处**设计缺陷**（本次全部修掉）

**① 信标不广播自己的信道号 → 设备只能"从听到的频点反推信道"**（协议 v1/v2）
两板相距十几厘米时**邻道泄漏**极强：网关在 474MHz 发射，设备却在 472MHz 上解出了信标
（实测日志 `scan ch1(472.0MHz): 5 beacon(s)`，而网关 `rf0 474.0MHz`）→ 设备锁到"错的信道"、
把 JOIN 发到网关听不到的频点 → 永远注册不上。上午的 **488/504MHz "幻影信道"**（±16/±32MHz
镜像，恰好落在 470+2k 栅格上）是同一个病根。

**修法（协议 v3）**：信标**自报信道号**，设备**采信信标说的号**（不再靠扫描命中点推断）：
```
信标 v3：计数(2B) | (信道号<<3)|(注册窗子槽数&7) | mapVer<<5|N | 协议版本(1B)
```
`scanForBeacon` 的候选信道改用 `beaconCh`；`lockFromBeacon` 发现与扫描命中点不同会打印
`信标自报信道 ch2(474.0MHz)（与扫描命中点不同）→ 改用它` 并**立刻调谐过去**；锁相前无条件重调谐。

**② 短号（`DEV_IDX`）自报 → 撞号 + 每块板要单独编译**
`DEV_IDX`/`DEVICE_ID` 原为编译期常量：两块板刷同一份固件 → 同号 ✗；并且 `DEV_IDX` 只有 8 位，
几十台设备必然碰撞（生日问题）。

**修法**：
- **身份从芯片 MAC 自动派生**（换板无需重编固件）：`G` + MAC 后 3 字节的 base32（5 字节 deviceId，
  `G` 前缀标明枪端；头盔用 `H`）。**必须用 `esp_read_mac()`** —— 实测 `ESP.getEfuseMac()` 在
  **ESP32-S3 上返回值的低字节与真实 MAC 不一致**，两块不同的板算出了同一个 `GC6T4` ✗✗
  （→ 网关把它们当成同一台设备，第二块永远注册不上 —— 这是当天最后一个大坑）。
- **短号由网关分配**：网关按身份串认设备，分配最小未用号，随 `TF_ASSIGN.payload[4]` 下发；
  设备收到后改用分配号（打印 `采用网关分配的 devIdx=N`）。寻址用 `lastJoinIdx`（设备当前自报号）
  → 设备无论是否已换号都收得到。

**③ 超帧相位漂移无法自愈 → 无限重发 JOIN**
设备相位靠 `lockFromBeacon(rxEnd - T_AIR)` 校正，但**前提是"信标落在预期的信标窗里"**。
晶振漂移（~20ppm × 14 分钟 ≈ 16ms）后信标落到设备预期的**下行窗**里（实测
`信标窗0帧 下行窗18帧`）→ 校正永不执行 → 漂移累积；同时它的注册窗帧早到约 10ms，
落进网关的**设备时隙窗**（`reg=0 slot=5`）。现象是设备 `assigned=0 mapVer=0` 且无限 `join try`。

**修法**：信标窗接收期限**放宽 20ms**（晚到的信标走**同一分支** → 锁相 → `sfStart=_sfStartUs`
→ 下一超帧自动对齐）。这是结构性修复：不依赖"恰好准时收到"。

### 8.3 三处**容量/体验改进**（本次落地）

| 改进 | 做法 | 效果 |
| --- | --- | --- |
| 注册快 | **NVS 记住上次成功的信道**，开机先只试它（~250ms），失手才回退全表扫描；开局前 3 次 JOIN **连续尝试**（不退避） | 注册从 ~10s 降到 ~1s（首刷无记录仍全表扫描一次） |
| 掉线快 | 两级超时：**12s 预警** + **20s 判定掉线**（原 30s 静默清理）。20s 是为容忍偶尔丢一次心跳（心跳 10s，设 15s 会误判） | 掉线感知从 30s 提前到 20s，且有预警行 |
| 下行保护 | ASSIGN 补发**只对注册窗 JOIN**（+每设备 1s 节流） | 补发率天然 ≤1 帧/超帧 = 下行容量本身，不再饿死 W/S/E |

**注册窗自适应**：有新设备注册后临时开 **3 个子槽**（5s 刷新），静默后缩回 1 个 ——
稳态超帧仍是 `37+10N ms`。子槽数随信标广播，两端据此算相同超帧长度。

### 8.4 实测经验（值得记住的坑）

1. **协议版本号必须有**：一次格式变更要同时改「发送端 / 接收解析 / 扫描取证」三处；
   当天漏改 `dwellBeacon` 导致 `counter=NO`、候选全被标"未确证"（§6.4）。
   `TDMA_PROTO_VER` 现在随信标整字节广播，版本不符会**明确报警**而不是静默跑偏。
2. **tx 完成 ≠ 辐射出去**：`TX_DONE` 只代表芯片发完；Ra-01S 的 RF 开关由 DIO2 驱动，
   漏发该命令或 PA/天线异常时芯片照样报 TX_DONE → 判"辐射"必须用对端（`lora-rx`）。
3. **两板近场互扰是真实存在的**：10cm 内两块板互相能收到对方帧（日志出现
   `信标窗收到 type=0x01 devIdx=1`＝收到另一台的 JOIN、`type=0x05`＝收到另一台的心跳），
   会互相压窗、拖慢注册。**台面测试建议拉开 ≥1m 或临时换信道。**
4. **网关每次开机可能换信道**（`assignFreqs` 按噪声质量选 k）：现场对设备不友好
   （设备要重扫/重注册）。后续可考虑 NVS 记忆或固定基准信道。
