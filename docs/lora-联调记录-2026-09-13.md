# LoRa 联调记录 · 2026-09-13（单信道闭环打通）

> 目标：**先把单信道闭环跑通**（枪端扫描选频 → 锁相 → JOIN → 收到 ASSIGN → 在自身时隙发帧）。
> 结论：**已打通，并稳定运行 5 分钟**（网关 `devs=1` 全程不掉、无 `expire`、`devHb` 序号连续）。
>
> 起点是"网关开机 `FATAL: no radio up`、枪端永远 `reg=no`"，一路查出 9 个独立缺陷。
> 本文按"现象 → 根因 → 修法 → 证据"记录，供后续接续。

---

## 1. 最终验证证据（2026-09-13 下午）

网关（COM14）连续 5 分钟日志的关键行：

```
[gw] t=31s  rf=1 ip=- ws=down | rf0 472.0MHz k=1 devs=1
...
[tdma] ch1 re-assign dev=1 slot=0 N=1 ver=1 (设备重复 JOIN，补发 ASSIGN)
[up] ch0 devHello idx=1 dev=G0001
[up-json] {"t":"devHb","gatewayId":"GW1","deviceId":"G0001","seq":5}
...
[gw] t=313s rf=1 ip=- ws=down | rf0 472.0MHz k=1 devs=1      ← 5 分钟内从未 expire
```

枪端关键行：

```
[tdma] scan ch1(472.0MHz): 5 beacon(s), counter=ok(sf=82), N=1
[tdma] 候选信道: ch1(确证)
[tdma] ch1 selected (balanced), N=1 ver=0
[tdma] assigned ch1 slot0 N1 ver1        ★ 下行通 = 闭环成立
[gun] t=… TDMA=run+locked ch=1 slot=0 … reg=no
```

> `reg=no` **不是故障**：枪端的 `reg` = `g_registered`，只有当它收到**服务器下发的
> TF_WELCOME（W）帧**时才置真。当前网关 `GW_WIFI_ENABLE=0`（WiFi 整体关闭），
> 没有服务器也就没有 W 帧 → 恒为 `no`。射频/MAC 层的注册标志是 `assigned` ✓。

## 2. 九个缺陷（现象 → 根因 → 修法）

### 2.1 网关开机误报 `FATAL: no radio up`（自检探针把矛头指向"焊接/供电"）

- **现象**：刷 `gateway` 后每 2s 重复 `FATAL: no radio up … 本机已检测到 0 个槽位`。
- **根因**：`probeSlot()` 跑在 `RadioLink::begin()` **之前**，而全工程唯一驱动 RST 的地方是
  RadioLib 的 `SX126x::reset()`（在 `begin()` 里）。G46 是 ESP32-S3 的 strapping 脚，
  未配置时由内部弱上拉/下拉决定电平，NRESET 被 SX1268 内部 ~50k 上拉与 S3 弱下拉分压
  ≈1.6V → 落在阈值不确定区 → 芯片可能一直停在复位态、SPI 不应答。
  对照：`spi-read` 能读到版本串，正因为它显式驱动 RST 并做复位脉冲。
  另有两处错：探针读的是 **0x0333**（RadioLib 未定义），版本串在 **0x0320**；
  且把 `rx[3]` 当数据首字节（实际是**状态字节**，数据从 `rx[4]` 起）。
- **修法**（`gateway/src/main.cpp`）：探针自己 `pinMode(rst,OUTPUT)` + 拉高 + 2ms 复位脉冲，
  先读一次 RST 原始电平（`before=` 诊断），再读 0x0320 十六字节并按 `ver="SX126…"` 判在位。

### 2.2 网关 WiFi 段阻塞开机（即使射频起来了也看不到心跳）

- **现象**：`setup()` 末尾 `while (WiFi.status() != WL_CONNECTED) { delay(500); }`，
  而 SSID/服务器是占位值 → 永远连不上、`loop()` 一行都不跑。
- **修法**：新增总开关 `GW_WIFI_ENABLE 0` + `GW_MIRROR_UPLINK_SERIAL 1`
  （本该发服务器的 JSON 镜像成串口 `[up-json]` 行 → 不接服务器也能看见上行内容）。
  副产品：WiFi+mbedTLS 不再链接，RAM 63.5KB→36KB、Flash 950KB→327KB。

### 2.3 OLED / 状态灯是"经典 ESP32 残留引脚"

- **现象**：网关 OLED 不亮、状态灯不亮。
- **根因**：`PIN_OLED_SDA/SCL = 21/22` 是经典 ESP32 的默认 I2C 脚，而 **ESP32-S3 没有 GPIO22**；
  `PIN_STATUS_LED = 2` 是经典板载 LED 脚，S3 上 G2 是空脚（枪端把 G2 当按键用）。
- **修法**：OLED 改 **G17/G18**（与枪端一致，代码零改动——两端都是 `U8G2_SSD1306_128X64_NONAME_F_SW_I2C`）；
  状态灯改 **G48**（模组板载 LED，**普通单色灯、不是 WS2812**、灌电流接法 → **低电平点亮**）。
  枪端 `LedStrip` 随之从 FastLED/WS2812 改写为单色版（"颜色"→**闪烁节奏**），
  接口不变、调用点不动，`gun/platformio.ini` 的 `fastled` 依赖移除。

### 2.4 扫描选频靠"随机平局" → 锁到假信标

- **现象**：枪端 `ch17 selected`（504MHz），而网关在 472MHz → 永远注册不上。
- **根因**：`scan` 只按 `score = N*100 + random(0..99)` 打分，两个候选 N 相同就**纯随机**。
- **修法**：**确证式扫描**——单频点停留 250ms，收满窗内所有帧，统计"信标个数 ≥2"且
  "超帧计数器逐一递增"才判定为本网网关；未确证的只作兜底。负载均衡（按 N 择优）保留。

### 2.5 幻影信道：+16MHz / +32MHz 杂散

- **现象**：扫描同时"确证"了 ch1(472)、ch9(488)、ch17(504) 三个频点，且都 `counter=ok`。
- **根因**：当时只有**一块**网关板在 472MHz 发射。`472+16=488`、`472+32=504`
  （16 = 晶振 32MHz/2）——两板相距十几厘米时电平足够强，**杂散被解成完整合法包**。
  栅格是 `470+2k`、470 以下无信道 → 只有正向偏移落在栅格点上，恰好 ch9/ch17。
- **修法**：2.4 的确证式扫描 + **注册自愈**（见 2.6）。这是**间歇性**故障：后一次扫描就只
  确证了 ch1 —— 所以两道保险必须长期保留。附带结论：网关开机扫描测到的
  `freq 18/19 (506/508MHz) avg=-36 max=-36` 也是近场泄漏把接收机压住的表现。

### 2.6 ASSIGN 只发一次 → 丢一次就永久注册不上

- **现象**：网关 `devs=1`、`join` 只打印一次，但设备每 600ms 重发 JOIN，永不进入时隙。
- **根因**：`onGwUplink` 对"已登记设备"直接 `return`；而 ASSIGN 只在首次 JOIN 时入队一次，
  网关每超帧又只发 1 帧下行 → 那帧丢了就再无重发。
- **修法**：对已登记设备的**重复 JOIN 补发 ASSIGN**（`sendAssign()`，**不重排**，slot/N/ver 不变，
  幂等）；`slot=0xFF`（信道满）改走 `advanceCandidate()` 换候选信道（原先"重新全表扫描"
  可能又选回同一满信道）。

### 2.7 mapVer 位宽不一致（潜伏 bug，一并修掉）

- 信标里 `mapVer` 只有 **3 bit**（`payload[4] = (mapVer<<5) | N`），而 ASSIGN 发的是整个字节，
  设备端却直接比较 `_beaconMapVer == _mapVer` → **`_mapVer ≥ 8` 时永远对不上**，
  症状与 2.6 一模一样。修法：ASSIGN 侧统一 `(_mapVer & 0x07)`。

### 2.8 【关键】下行全丢：信标窗与下行窗之间没有重新武装 RX

- **现象**：网关日志明确显示"每次收到 JOIN 就补发 ASSIGN"（`re-assign` 刷屏、`devs=1`），
  而枪端 30 秒内一次都没进 `assigned` —— **上行通、下行全丢**。
- **根因**：原实现把信标窗与下行窗写成**两次独立轮询**，注释里"射频仍在 RX（连续模式，
  未重武装）必然被捕获"是**错误假设**——RX_DONE 之后芯片并不保证留在 RX。
  网关下行帧在信标结束后约 **1ms** 就发，**前导只有 4 符号（SF7/BW500k ≈ 2.1ms）**，
  错过前导整帧即丢；而轮询粒度是 `vTaskDelay(1)` = **1ms**，足以错过。
- **修法**：① 读完信标**立刻重新武装 RX** 再进下行窗；② 两个窗都改**细粒度轮询**
  （`delayMicroseconds(200)`，`readPacketPoll(..., fine=true)`）；
  ③ 抽出 `applyAssign()`，ASSIGN 落在信标窗尾也一并消费（原先会被当普通帧丢进应用队列，MAC 永远看不到）。
- **同一根因的第二个症状（顺带修好）**：粗粒度轮询让设备相位基准偏晚约 1ms，
  JOIN 落在网关注册窗（`T_REG 10ms + 6ms 余量`）边缘被大量漏掉——这解释了修复前
  "60 秒只收到 4 次 JOIN、`re-assign` 每 5~6 秒才一次"。

### 2.9 `txFrame()` 起发失败静默

- 原来 `if (_r->startTransmit(...) != RADIOLIB_ERR_NONE) return;` —— 帧已被 `ringPop` 出队，
  一旦起发失败就**永久丢失**且无任何日志。现改为打印 `txFrame: startTransmit 失败，该帧丢失`。

## 3. 当前能力与已知限制（单信道）

| 项 | 现状 |
| --- | --- |
| 吞吐 | 单信道 17 时隙；超帧 `30+10N ms`（N=1 → 47ms；N=17 → 200ms） |
| 上下行 | 上行：每设备每超帧 1 帧；**下行：每超帧只有 1 帧** ← 瓶颈 |
| 注册 | 每超帧 1 个注册窗（10ms = 1 帧容量）；设备每 3 超帧试一次 + 0~6ms 抖动 |
| 稳定性 | 5 分钟 `devs=1` 不掉、无 `expire` ✓ |

**两个必须在 50 台目标前解决的问题：**

1. **下行容量**：每超帧只有 1 帧 = N=17 时 5 帧/s。当前每个补发的 ASSIGN 都要占这一帧，
   而枪端应用层每 5s 就重发一次 J 帧（等 W 帧）→ 50 台时会有 ~10 次/s 的 ASSIGN 请求，
   **远超下行窗排水能力，会把下行窗占满**（W/S/E 等下行帧被饿死）。
   → 需要"**每设备补发 ASSIGN 节流**"（如每台 ≥2s 一次），或加宽下行窗。
2. **注册重试太密**：设备"每 3 超帧"确定性重试 + 单注册窗（一窗一帧）→ 50 台冷启动会撞死
   （按时隙 ALOHA 估算，G≈5.7 时每窗成功率仅 ~0.02，收敛可能要分钟级）。
   → 需要"**真·时隙 ALOHA**"（随机子槽 + 随机重试间隔）+ **自适应注册窗**（有未注册设备时
   临时开 2~3 个子槽，稳态缩回 1 个，保证 N=17 时超帧仍是 200ms）。
